代表ページの観察を初期段階に限定し、生成コードを固定した後は追加のLLM判断なしでHTML保存まで実行できた。対象は事前に選んだ6サイトで、全80サイトへの汎用性を示す結果ではない。

LLMに提示した代表ページは計15 URL（1サイト最大3 URL。一覧のスクロール前後DOMも初期観測として提示）。修正後の同型詳細試験では6/6サイト・18件、本文未観測の別一覧候補では4/6サイト・12件の新規HTMLと描画後DOMを保存した。すべて実際に観測したリンクをたどり、代表本文URLとcold取得済みURLを除外した。

## 再利用・動的操作

スクロール前にはなかったリンクから保存したHTMLは6件（09と10で各3件）。スクロール途中のDOM・状態IDとリンクの出所を保存して確認した。この6件は既存の目的型判定器では未確定。02の通常ページ送りも実行したが、ページ送りによる増加と同一URLでのスクロール増加は別扱いとした。

coldは学習した一覧を再訪して、代表では本文を見せていない別の詳細へ進む試験。warmは別の一覧/ナビゲーション候補へ同じコードを適用する試験。どちらも追加のページ本文をLLMへ渡さず、生成コードを変更せずに別Nodeプロセス・新規ブラウザcontextで実行した。グラフ最短経路検索Gは未実装・未測定。

02の別入口候補は商品一覧ではなくdocumentation、10はdrill-downで、学習した一覧の構造と異なり対象リンクを保存できなかった。候補選定の問題・未対応のページ型と、同じ型への規則適用失敗を混同しない。1種類の一覧だけからサイト全体の操作型へ一般化できたとはいえない。

## 評価の限界

評価条件と候補選定手順は生成前に固定し、別一覧の取得・候補URL固定もコード生成前に行った。評価側のHTML、候補URL集合、専用セレクタを生成担当へ渡していない。固定したURLは一般的なリンク形状から選んだ候補で、すべての本文・目的型を独立確認した正解集合ではない。したがって固定URLの意味的な再現率は未計測とする。

固定候補は計13件、保存到達の照合結果は3件（サイト別: {"01": 0, "02": 0, "09": 3, "14": 0, "67": 0}）。この数字を目的ページの網羅率とは扱わない。

既存の型判定器はProductの構造化データまたは購入操作等を要求する。書籍デモやメーカーの製品カタログなどは、その条件を満たさず保留になり得る。実験結果に合わせて判定器を変更していない。SKU・価格・属性抽出の精度は採点していない。

## 実行器の修正

最初の実行で10/67が保存0件となった。原因は実行器のAPI契約の不一致だった。宣言済みのmax_loop_iterationsを入力へ渡していなかったことと、scrollの返却値に含まれる実観測リンクをsave側の観測済み集合へ登録していなかったことを修正した。

生成コードは1バイトも変更せず、該当2サイトだけ別repair-runで再実行した。修正前12試行と修正後4試行を保存し、予算・費用は引き継いだ。LLMによるコード修復、正解URLの埋込み、人手によるサイト別セレクタ補正は0。生成前の共通API開発・修正は別作業として記録する。

要求モデルはgpt-6-luna。サンプリング2ジョブ＋コード生成6ジョブ、初期配信失敗2ジョブも別記。要求ファイルはsampling 215,077文字、generation 539,711文字だが、実際のnative入力トークン・出力・内部推論回数・料金は取得できず不明。実モデルIDの独立確認もできない。開発・最終報告のモデル量は別枠で不明。

取得実行プロセスの外部モデル呼出し・ローカル推論は全16試行で0。将来のページ型変更時の修復費用や10/30/100連続取得は未測定。今回の結果だけから大量処理時の単価や安さは断定しない。新たな有料クラウド・外部推論APIは使用していない。

## 採否・Skillへの統合案

代表HTMLを使う方式は、URL群だけで判断した前回より検証を続ける価値がある。1サイトの初期調査をコンパイラのように扱い、ページ型ごとに生成コード・観測条件・停止条件を保存し、以後の取得をプログラムへ任せる構成を採用候補にする。既存Skillへ即時に汎用機能として組み込む段階ではない。

次に必要なのは、代表ページ上でのコードの事前実行検証、既存の判定器が扱えないページ型の独立評価、一覧候補の妥当性確認、未知の操作型を検出したときの停止と初期調査のやり直し。毎ページをLLMへ戻す設計にはしない。ブラウザ/HTTPの切替と大量処理は別条件で測り、今回の経路生成の成績へ混ぜない。
